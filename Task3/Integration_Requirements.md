# Задание 3. Внешние интеграции «Умного дома»: требования безопасности

Новые услуги: **интеллектуальный домофон** (открытие по звонку, распознавание лиц — биометрия, автоматическое открытие при разрешённом доступе) и **интеллектуальный шлагбаум** (автоматический въезд по распознаванию номеров). Сервисы предоставляет **внешний партнёр** через свою платформу; доступны через текущее мобильное приложение собственников.

Артефакты: `C4_Context_SmartHome.png` (+`.puml`) — контекст; `PropDevelopment_C4_updated.drawio` — доработанная диаграмма контейнеров: добавлены контейнер **smart-home-gateway** (единая точка интеграции внутри PropDevelopment) и внешняя **Платформа «Умный дом» партнёра**, со связями от мобильного приложения, CRM собственников и к платформе партнёра.

## Почему в ландшафте появляется smart-home-gateway

Проблемы PropDevelopment из кейса: партнёрские API используются «без единых политик по безопасности и без системного контроля за передаваемыми данными», партнёры одной УК видят данные другой. Чтобы не воспроизвести эти проблемы с новым партнёром, вся интеграция идёт через один собственный контейнер-шлюз, где сосредоточены аутентификация, авторизация, минимизация данных и аудит. Приложение собственников и CRM не общаются с платформой партнёра напрямую.

## 1. Требования к безопасности

**Передача данных**

- Весь трафик — только по TLS 1.2+; канал PropDevelopment ↔ партнёр — взаимный mTLS с клиентскими сертификатами.
- Минимизация данных: партнёру передаются только данные, необходимые для функции (идентификатор доступа/токен, идентификатор объекта, разрешающая команда). Номера квартир, ФИО, контакты, состав семьи — не передаются.
- Токены доступа не передаются в URL-параметрах (только заголовки) — защита от перехвата и попадания в логи.
- Биометрия (шаблоны лиц) и распознанные номера **не покидают платформу партнёра**; в PropDevelopment возвращаются только события доступа (кто/когда/разрешено) без биометрических данных. Обработка биометрии регулируется 152-ФЗ (специальные категории) — собирается отдельное информированное согласие собственника, хранится у владельца данных.

**Разграничение доступа**

- Партнёр получает доступ только к своим объектам: проверка «объект ↔ партнёр ↔ собственник» на каждый запрос в smart-home-gateway (по данным CRM собственников) — устраняет сценарий «партнёр одной УК видит чужие ЖК».
- Права собственника проверяются на каждой команде (домофон/шлагбаум только для своего объекта): авторизация на уровне объекта, а не только аутентификация пользователя.
- Принцип минимальных привилегий для сервисных учёток интеграции; отдельная учётная запись (сервисный аккаунт) на партнёра, без общих ключей.

**Аудит и реагирование**

- Все вызовы шлюза журналируются: кто, когда, какой объект, результат (JSON-логи: timestamp, event_id, event_type, user_id, result, details); логи шифруются, хранятся в централизованном хранилище.
- Оповещения службы безопасности об аномалиях: серии отказов авторизации, обращения к чужим объектам, нестандартные объёмы вызовов (интеграция с SIEM).
- Инциденты партнёра (компрометация его платформы) не должны открывать доступ в PropDevelopment: у партнёра нет долгоживущих ключей к нашим системам — только short-lived токены, выдаваемые шлюзом.

## 2. Протоколы аутентификации и авторизации

- **Аутентификация собственника** — в мобильном приложении через существующий auth-service (Keycloak): OAuth 2.0 / OpenID Connect, MFA; приложению выдаётся access token (JWT, короткий TTL) + refresh token.
- **Авторизация собственника** — проверка JWT-клеймов в smart-home-gateway + запрос прав на объект в CRM (RBAC по роли «собственник/жилец», ABAC по атрибуту объекта владения).
- **Аутентификация платформы партнёра** — OAuth 2.0 Client Credentials Grant: партнёр получает client_id/secret (или mTLS-сертификат как client-аутентификацию), шлюз выдаёт short-lived токен (15–60 мин).
- **Авторизация партнёра** — scope-based: токен партнёра ограничен scope `smart-home-devices` и перечнем закреплённых объектов; проверка на каждый запрос.
- **Вебхуки партнёра** (события: звонок в домофон, факт открытия, распознанный въезд) — подписанные запросы (HMAC-подпись тела + метка времени против replay-атак), приём только с зафиксированных адресов партнёра.

## 3. Организация взаимодействия

- **Единая точка**: мобильное приложение → smart-home-gateway → платформа партнёра. Прямых интеграций приложение↔партнёр и CRM↔партнёр нет — политика повторяет рекомендацию ADR курса «централизованный API Gateway для контроля доступа к внешним и внутренним API».
- **Синхронный контур**: команды (открыть дверь/шлагбаум, конфигурация доступа) — REST/JSON через mTLS, таймауты и ретраи с идемпотентными ключами.
- **Асинхронный контур**: события доступа и статусы устройств — вебхуки партнёра в шлюз с последующей публикацией в Kafka для доменов ЖКУ и «Дата» (переиспользование существующей шины).
- **SLA и договор**: время ответа команды открытия, доступность платформы, порядок реагирования на инциденты, ограничения на обработку биометрии (152-ФЗ), право аудита — фиксируются в договоре с партнёром до запуска.
- **Обновление без простоя**: версиярование API партнёра (`/v1/...`), контракт через OpenAPI-спецификацию; изменения согласовываются через шлюз без мобилизации клиентов.
